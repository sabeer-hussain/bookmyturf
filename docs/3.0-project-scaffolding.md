# BookMyTurf — Project Scaffolding (3.0)

## Overview

Phase 3 sets up the complete monorepo structure with all tools, configurations, and empty module skeletons. No business logic is implemented — only the foundation that Phase 4 builds on.

---

## Monorepo Architecture

```
bookmyturf/
├── apps/
│   ├── api/          → NestJS backend (port 4000)
│   └── web/          → Next.js frontend (port 3000)
├── packages/
│   ├── tsconfig/     → Shared TypeScript configurations
│   ├── eslint-config/→ Shared linting rules
│   └── shared/       → Shared types, constants, enums
├── docs/             → All project documentation
└── [root configs]    → Turborepo, pnpm, Docker, CI/CD
```

### Why Monorepo?

- One `pnpm dev` starts both apps
- Shared types between frontend and backend (no type drift)
- Single CI/CD pipeline
- Unified code formatting and linting
- Single PR for full-stack features

Shared linting rules:

| Config    | Used by  | Extends                                            |
| --------- | -------- | -------------------------------------------------- |
| `base.js` | All      | eslint:recommended + @typescript-eslint + prettier |
| `nest.js` | apps/api | base + node env + jest env                         |
| `next.js` | apps/web | base + next/core-web-vitals                        |

Each app and package has a `.eslintrc.js` that extends its respective shared config.

Code shared between frontend and backend:

- Helmet security headers
- CORS configured from env
- Global ValidationPipe (whitelist, forbidNonWhitelisted, transform)
- Global prefix: `/v1`
- Swagger docs at `/api/docs`
- Port: 4000

**Root module:** `src/app.module.ts`

## Local Development

### Start services

```bash
docker-compose up -d          # PostgreSQL (5432) + Redis (6379)
pnpm dev                      # Frontend (3000) + Backend (4000)
```

### Database

```bash
cd apps/api
```

## How to Extend (Phase 4 Guide)

### Adding a new API endpoint

1. Open the relevant module (e.g., `apps/api/src/modules/bookings/`)
2. Add DTO in `dto/` folder
3. Add method in `*.service.ts`
4. Add route in `*.controller.ts`
5. Import types from `@bookmyturf/shared`

### Adding a new page

1. Create `page.tsx` in the appropriate route group
2. Import components from `@/components`
3. Use hooks from `@/hooks` for data fetching

### Adding a shared type

1. Add to `packages/shared/src/types/`
2. Export from `packages/shared/src/types/index.ts`
3. Available in both apps via `import { ... } from '@bookmyturf/shared'`

### Adding a shadcn/ui component

```bash
cd apps/web
pnpm dlx shadcn-ui@latest add button
```

## Git Hooks (Pre-commit Checks)

Automated checks run before every commit via **Husky + lint-staged + commitlint**:

### Pre-commit Hook

Runs on staged files before commit is created:

- **Prettier** — auto-formats `.ts`, `.tsx`, `.json`, `.md`, `.yml` files

### Commit-msg Hook

Validates commit message format:

- Must follow [Conventional Commits](https://www.conventionalcommits.org/) format
- Pattern: `type: description`

**Allowed types:**

| Type        | When to use                          |
| ----------- | ------------------------------------ |
| `feat:`     | New feature                          |
| `fix:`      | Bug fix                              |
| `docs:`     | Documentation only                   |
| `chore:`    | Tooling, dependencies, config        |
| `refactor:` | Code restructure (no feature change) |
| `test:`     | Adding/updating tests                |
| `style:`    | Formatting (no logic change)         |
| `perf:`     | Performance improvement              |
| `ci:`       | CI/CD pipeline changes               |

**Examples:**

```bash
git commit -m "feat: add booking creation API"      ✅
git commit -m "fix: resolve double-booking issue"   ✅
git commit -m "docs: update API design document"    ✅
git commit -m "updated stuff"                       ❌ blocked
git commit -m "Fixed the bug"                       ❌ blocked
```
