# BookMyTurf — Design Validation (1.3)

## Overview
After business decisions (1.2) were made, these 7 design questions were asked to validate architectural choices before proceeding to system design.

---

## Validated Design Decisions

| # | Question | Options | Final Choice | Impact on Architecture |
|---|----------|---------|--------------|----------------------|
| 1 | Venue structure per tenant | Single venue / Multiple venues | **Multiple venues** | Tenant → Venue → Court hierarchy |
| 2 | Booking payment flow | Pay first / Reserve then pay / Hybrid (online + offline) | **Hybrid (online + offline)** | Booking has `source`, `heldUntil`, `paidOffline` fields; cron job to expire held slots |
| 3 | Slot booking granularity | 30 min fixed / 1 hour fixed / Configurable per court-sport | **Configurable per court-sport** | `baseSlotMinutes` in CourtSport model |
| 4 | Customer account requirement | Mandatory login / Browse free, login at checkout / Guest checkout | **Browse free, login at checkout** | Public availability API needs no auth; auth required only at POST /bookings |
| 5 | Tenant onboarding approval | Self-serve instant / Admin approval / Self-serve with trial | **Self-serve with 14-day trial** | Auto-create Subscription (status: TRIAL, trialEndsAt: +14 days) on tenant signup |
| 6 | Data backup & recovery | Automated backups only / + Point-in-time / + Soft deletes | **All three (automated + PITR + soft deletes)** | RDS PITR enabled; `isActive` field on all entities; no hard deletes |
| 7 | Pricing display to customer | Price per slot visible / Breakdown at checkout / All-inclusive | **All-inclusive** | Customer sees one price; `platformFee` calculated server-side from `commissionRate` in Plan |

---

## Detailed Reasoning

### DV1: Multiple Venues per Tenant
- Real turf owners often have 2+ branches
- Schema supports single venue too (just don't create more)
- Subscription plan limits control max venues per tier

### DV2: Hybrid Payment Flow (Online + Offline)
- Real turfs have 50-90% walk-in customers who pay at counter
- Online: Customer selects slots → 10-min hold → Pay via Razorpay → Confirmed
- Offline: Staff creates booking → marks "paid at counter" → No Razorpay flow
- Ensures 100% of bookings tracked in one system

### DV3: Configurable Slot Duration per Court-Sport
- Badminton = 30 min, Cricket = 60 min, Football = 60 min
- Turf owner knows ideal duration for each sport
- `baseSlotMinutes` field in CourtSport model handles this

### DV4: Browse Free, Login at Checkout
- Zero friction for discovery (shared WhatsApp link → see slots immediately)
- No login wall before viewing availability = higher conversion
- Login at checkout ensures verified contact for notifications
- Same model as Amazon, Swiggy, Urban Company

### DV5: Self-serve with 14-day Trial
- Zero friction for growth (no admin bottleneck)
- Owner experiences value before paying
- Trial auto-created on signup (Pro plan features for 14 days)
- Bad actors can be deactivated from admin panel

### DV6: Automated Backups + PITR + Soft Deletes
- RDS daily backups + point-in-time recovery (restore to any second, 7 days)
- Soft deletes (`isActive: false`) prevent accidental data loss at app level
- Multi-tenant = one wrong query can affect multiple tenants — need recovery layers
- Zero extra cost (PITR is free on RDS)

### DV7: All-inclusive Pricing
- Customer sees "₹800/hour" — clear, no confusion
- Hidden fees at checkout kill conversion
- Platform commission deducted from turf owner's payout (B2B concern, not customer concern)
- Same model as Swiggy, Uber (customer pays X, platform takes cut from merchant)
