# BookMyTurf — Database Schema (2.2)

## Overview

- **Database:** PostgreSQL (AWS RDS)
- **ORM:** Prisma
- **Multi-tenancy:** Shared schema with `tenantId` column + Row-Level Security (RLS)
- **Naming:** camelCase in Prisma, snake_case in actual DB (via `@map`)

---

## Entity Relationship Summary

```
Tenant (1) ──→ (N) Venue ──→ (N) Court ──→ (N) CourtSport
                                    │                │
                                    ▼                ▼
                              SlotConfig         Booking ──→ Payment
                                                    │
                                                    ▼
                                              BookingSlot

Tenant (1) ──→ (N) User (staff/managers)
Tenant (1) ──→ (1) Subscription ──→ Plan
Tenant (1) ──→ (1) CancellationPolicy
Customer (User) ──→ (N) Booking
```

  finalAmount     Decimal       @db.Decimal(10, 2)
  status          BookingStatus @default(PENDING)
  source          BookingSource @default(ONLINE)  // online, walk-in, phone

  // Relations

  @@index([courtSportId])

## Row-Level Security (RLS) Strategy

Applied via Prisma middleware (not PostgreSQL-native RLS) for flexibility:

```typescript
// prisma.service.ts — Tenant isolation middleware
prisma.$use(async (params, next) => {
  // Inject tenantId filter on all read queries
  if (params.action === 'findMany' || params.action === 'findFirst') {
    params.args.where = { ...params.args.where, tenantId: currentTenantId };
  }
  // Inject tenantId on all create queries
  if (params.action === 'create') {
    params.args.data = { ...params.args.data, tenantId: currentTenantId };
  }
  return next(params);
});
```

## Key Design Decisions

1. **`cuid()` for IDs** — URL-safe, sortable, no sequential exposure (prevents enumeration attacks)
2. **`tenantId` on Booking/Payment** — Denormalized for faster queries (avoids joining through CourtSport → Court → Venue → Tenant)
3. **Separate `BookingSlot` table** — Supports consecutive slot bookings while keeping availability queries simple
4. **`CourtSport` junction** — One court can support multiple sports with different pricing/duration
5. **`SlotConfig` per day** — Allows different schedules on weekdays vs weekends
6. **`AuditLog`** — Critical for SaaS compliance, debugging disputes, and refund tracking
7. **Soft delete via `isActive`** — No hard deletes on business entities (tenants, venues, courts, users, bookings, payments). Configuration/junction tables (e.g., CourtSport) may use hard delete when no business history is attached.
8. **`Decimal` for money** — Avoids floating-point precision issues
9. **Platform fee in Payment** — Tracks commission split for reconciliation
10. **JSON fields** — Used for flexible data (amenities, features, custom rules) that doesn't need relational querying
