# BookMyTurf — Auth Flow Documentation (4.1)

## Overview

Phone OTP + JWT authentication system with token rotation and rate limiting.

- **Provider:** MSG91 (production) / Dev mock (local)
- **Token strategy:** Access token (15min) + Refresh token (7 days) with rotation
- **Storage:** Redis (OTP, rate limits) + PostgreSQL (users, hashed refresh tokens)

---

## Complete Auth Flow

```
Customer → Send OTP → Verify OTP → Get Tokens → Access Protected Routes
                                         ↓
                              Token Expires (15min)
                                         ↓
                              Refresh Token → New Token Pair
                                         ↓
                              Refresh Expires (7 days)
                                         ↓
                              Re-login Required
```

---

## API Endpoints

### 1. POST /v1/auth/otp/send

**Purpose:** Send a 6-digit OTP to the customer's phone number.

**Auth:** Public (no token required)

**Request:**
| Field | Type | Required | Validation | Description |
|-------|------|----------|------------|-------------|
| phone | string | Yes | E.164 format (`/^\+[1-9]\d{10,14}$/`) | Customer phone (e.g., +919876543210) |

**What happens internally:**

1. Validates phone format (E.164)
2. Checks rate limit in Redis (`otp_rate:{phone}`) — max 3 sends per 10 minutes
3. Generates 6-digit OTP (dev mode: always `123456`)
4. Stores OTP in Redis with key `otp:{phone}` and 10-minute TTL
5. Calls OTP provider to send SMS (dev mode: logs to console)
6. Increments rate limit counter in Redis

**Response (201):**

```json
{
  "success": true,
  "data": {
    "message": "OTP sent successfully"
  }
}
```

**Error responses:**
| Code | Condition |
|------|-----------|
| 400 | Invalid phone format |
| 429 | Rate limit exceeded (3 sends in 10 minutes) |

**Redis keys used:**
| Key | Value | TTL |
|-----|-------|-----|
| `otp:{phone}` | 6-digit code | 600s (10min) |
| `otp_rate:{phone}` | Send count (1-3) | 600s (10min) |

### 2. POST /v1/auth/otp/verify

**Purpose:** Verify the OTP and return JWT tokens. Auto-creates user on first login.

**Auth:** Public (no token required)

**Request:**
| Field | Type | Required | Validation | Description |
|-------|------|----------|------------|-------------|
| phone | string | Yes | E.164 format | Phone number that received OTP |
| code | string | Yes | Exactly 6 digits (`/^\d{6}$/`) | OTP code to verify |

**What happens internally:**

1. Validates phone and code format
2. Increments attempt counter in Redis (`otp_attempts:{phone}`)
3. Rejects if attempts > 5 (brute force protection)
4. Retrieves stored OTP from Redis (`otp:{phone}`)
5. Compares submitted code with stored code
6. If valid: deletes OTP and attempt counter from Redis
7. Looks up user by phone in PostgreSQL
8. If user not found: creates new user (role: CUSTOMER, phoneVerified: true)
9. If user exists: updates lastLoginAt and phoneVerified
10. Generates access token (15min) and refresh token (7 days)
11. Hashes refresh token with bcrypt (10 rounds) and stores hash in user record
12. Returns tokens + sanitized user (without refreshToken hash)

**Response (201):**

```json
{
  "success": true,
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "refreshToken": "eyJhbGciOiJIUzI1NiIs...",
    "user": {
      "id": "cmqo2zbgj0000ilm1q1jqeadw",
      "phone": "+919876543210",
      "firstName": "User",
      "lastName": null,
      "email": null,
      "role": "CUSTOMER",
      "tenantId": null,
      "phoneVerified": true,
      "emailVerified": false,
      "isActive": true,
      "createdAt": "2026-06-21T...",
      "updatedAt": "2026-06-21T..."
    }
  }
}
```

**Error responses:**
| Code | Condition |
|------|-----------|
| 400 | Invalid format / Max attempts exceeded |
| 401 | Invalid or expired OTP |

**Redis keys used:**
| Key | Value | TTL |
|-----|-------|-----|
| `otp:{phone}` | Stored code (read + delete) | 600s |
| `otp_attempts:{phone}` | Attempt count (1-5) | 600s |

**JWT access token payload:**

```json
{ "sub": "user-id", "role": "CUSTOMER", "tenantId": null, "iat": 1719..., "exp": 1719... }
```

### 3. POST /v1/auth/refresh

**Purpose:** Exchange a valid refresh token for a new token pair (rotation).

**Auth:** Public (no Bearer token required, but refresh token in body)

**Request:**
| Field | Type | Required | Description |
|-------|------|----------|-------------|
| refreshToken | string | Yes | Refresh token from login or previous refresh |

**What happens internally:**

1. Verifies refresh token signature using JWT_REFRESH_SECRET
2. Extracts user ID from token payload
3. Looks up user in PostgreSQL
4. Compares submitted refresh token against stored bcrypt hash
5. If mismatch: rejects (token was already rotated or stolen)
6. Generates new access + refresh token pair
7. Hashes new refresh token and updates user record
8. Old refresh token is now invalid (rotation)

**Response (201):**

```json
{
  "success": true,
  "data": {
    "accessToken": "eyJ...(new)",
    "refreshToken": "eyJ...(new)"
  }
}
```

**Error responses:**
| Code | Condition |
|------|-----------|
| 400 | Missing refreshToken |
| 403 | Invalid/expired refresh token or token mismatch |

**Security:** Token rotation ensures that if a refresh token is stolen, it can only be used once. The legitimate user's next refresh will fail (hash mismatch), alerting them to compromise.

### 4. POST /v1/auth/logout

**Purpose:** Invalidate the user's refresh token (end session).

**Auth:** Required (Bearer access token)

**Request:** No body required. Token in Authorization header.

**What happens internally:**

1. JWT guard validates access token from Authorization header
2. Extracts user ID from token payload
3. Sets `refreshToken: null` in user record
4. Any subsequent refresh attempts will fail

**Response (201):**

```json
{
  "success": true,
  "data": {
    "message": "Logged out successfully"
  }
}
```

**Error responses:**
| Code | Condition |
|------|-----------|
| 401 | Missing or invalid access token |

**Note:** The access token remains valid until it expires (max 15min). For immediate invalidation, a token blacklist would be needed (not implemented for MVP).

### 5. GET /v1/auth/me

**Purpose:** Get the currently authenticated user's profile.

**Auth:** Required (Bearer access token)

**Request:** No body. Token in Authorization header.

**What happens internally:**

2. Extracts user ID from token payload
3. Fetches user from PostgreSQL by ID
4. Returns sanitized user (excludes refreshToken hash)

### 6. POST /v1/auth/google

**Purpose:** Login or signup using a Google ID token (obtained from frontend via @react-oauth/google).

**Auth:** Public (no token required)

**Request:**
| Field | Type | Required | Description |
|-------|------|----------|-------------|
| idToken | string | Yes | Google ID token from frontend OAuth flow |

**What happens internally:**

1. Checks if `GOOGLE_CLIENT_ID` is configured — if not, returns 401 with clear message
2. Verifies ID token with Google's API using `google-auth-library`
3. Extracts email, given_name, family_name, picture, Google sub ID from token payload
4. Looks up user by email in PostgreSQL
5. If not found, looks up by googleId
6. If new user: creates with role CUSTOMER, email, name, picture, emailVerified=true
7. If existing user without googleId: links Google account (adds googleId, updates avatar)
8. If existing user with googleId: updates lastLoginAt
9. Generates access + refresh token pair
10. Returns tokens + sanitized user

**Response (201):**

```json
{
  "success": true,
  "data": {
    "accessToken": "eyJ...",
    "refreshToken": "eyJ...",
    "user": {
      "id": "...",
      "email": "user@gmail.com",
      "firstName": "Rahul",
      "lastName": "Kumar",
      "avatar": "https://lh3.googleusercontent.com/...",
      "role": "CUSTOMER",
      "googleId": "1234567890",
      "emailVerified": true,
      "phoneVerified": false,
      "phone": null,
      "tenantId": null
    }
  }
}
```

**Error responses:**
| Code | Condition |
|------|-----------|
| 400 | Missing idToken |
| 401 | GOOGLE_CLIENT_ID not configured or invalid token |

**Account matching logic:**

- Match by email first, then by googleId
- No automatic phone-to-Google linking (security)
- Users who signed up via OTP and Google separately will have two accounts
- Account merging is a future feature (profile settings)

## Route Protection

### Global Guards (applied to ALL routes automatically)

| Guard          | Purpose        | Behavior                                                                                             |
| -------------- | -------------- | ---------------------------------------------------------------------------------------------------- |
| `JwtAuthGuard` | Authentication | Validates JWT access token. Returns 401 if missing/invalid/expired. Routes opt out with `@Public()`. |
| `RolesGuard`   | Authorization  | Checks `@Roles()` metadata. Returns 403 if user lacks required role. Skips if no roles specified.    |

### Per-Route Guard

| Guard         | Purpose          | Usage                                                                                                                    |
| ------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `TenantGuard` | Tenant isolation | Applied with `@UseGuards(TenantGuard)` on tenant-management routes. Checks `X-Tenant-Id` header matches user's tenantId. |

### Decorators

| Decorator                             | Purpose                | Example                                                             |
| ------------------------------------- | ---------------------- | ------------------------------------------------------------------- |
| `@Public()`                           | Skip authentication    | Health checks, OTP send/verify, refresh                             |
| `@Roles('TURF_OWNER', 'SUPER_ADMIN')` | Restrict by role       | Tenant management, admin routes                                     |
| `@CurrentUser()`                      | Get authenticated user | `@CurrentUser('sub')` for userId, `@CurrentUser()` for full payload |

### Middleware (runs before guards)

| Middleware                | Purpose                                                 |
| ------------------------- | ------------------------------------------------------- |
| `CorrelationIdMiddleware` | Generates/passes `x-correlation-id` for request tracing |
| `TenantMiddleware`        | Extracts `X-Tenant-Id` header into request context      |

### Interceptors (runs after guards, wraps response)

| Interceptor            | Purpose                                              |
| ---------------------- | ---------------------------------------------------- |
| `TransformInterceptor` | Wraps responses in `{ success: true, data: ... }`    |
| `LoggingInterceptor`   | Logs `METHOD /path STATUS duration` for each request |

### Request Pipeline Order

```
Request → CorrelationIdMiddleware → TenantMiddleware → JwtAuthGuard → RolesGuard → Controller → LoggingInterceptor → TransformInterceptor → Response
```

## Rate Limiting

| Limit                 | Value        | Window     | Key                      |
| --------------------- | ------------ | ---------- | ------------------------ |
| OTP sends per phone   | 3            | 10 minutes | `otp_rate:{phone}`       |
| OTP verify attempts   | 5            | 10 minutes | `otp_attempts:{phone}`   |
| Global API rate limit | 100 requests | 60 seconds | ThrottlerModule (per IP) |

---

## Security Measures

| Measure                | Implementation                                       |
| ---------------------- | ---------------------------------------------------- |
| Brute force protection | Max 5 OTP attempts, counter persists across resends  |
| Rate limiting          | Max 3 OTP sends per 10 min per phone                 |
| Token rotation         | Old refresh token invalidated on each refresh        |
| Hashed storage         | Refresh tokens stored as bcrypt hash (not plaintext) |
| Short-lived access     | 15-minute expiry limits exposure window              |
| Input validation       | E.164 phone format, 6-digit code, DTO whitelist      |
| Response sanitization  | refreshToken hash never returned to client           |

---

## Dev Mode Behavior

When `OTP_PROVIDER=dev`:

- OTP is always `123456` (no SMS sent)
- OTP code logged to console: `[DEV] OTP for +91...: 123456`
- All other logic (Redis storage, rate limiting, JWT) works identically
